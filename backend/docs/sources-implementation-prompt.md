# Промпт для backend-модели

Доработай Spring Boot API «Кадра» в `backend/`. Изучи `README.md`, Docker Compose, миграции Flyway, `MangaSource`, `MangaSourceRegistry`, контроллер каталога, DTO, обработчик ошибок, библиотеку и тесты. Сейчас зарегистрирован Pepper&Carrot, каталог обходит все адаптеры, библиотека хранится в PostgreSQL.

## Порядок работы

1. До изменения кода создай `backend/docs/sources-implementation-plan.md`. Опиши архитектуру, хранение состояния, REST-контракт, изменения каталога, совместимость и набор тестов.
2. После сохранения плана реализуй API и миграцию данных. Выполни тесты и проверь запросы к живым Spring Boot и PostgreSQL. Запускай Maven Wrapper и Docker Compose из `backend/` с существующим томом PostgreSQL.
3. Создай `backend/docs/sources-implementation-report.md`. Запиши изменения, примеры реальных запросов и ответов, команды, фактические результаты и отклонения от плана. Обнови `backend/README.md` с контрактом и ссылками на план и отчёт.

## Что реализовать

- «Расширение» — зарегистрированный серверный адаптер сайта. Формируй список из `MangaSourceRegistry` и публикуй только реально работающие адаптеры, начиная с Pepper&Carrot. Отдавай метаданные из локально известных данных. Для получения списка обращение к самому сайту не требуется.
- «Источник» — подключённый адаптер. Храни подключённые `sourceId` в PostgreSQL. Добавь новую миграцию Flyway с таблицей и стартовым Pepper&Carrot для чистой и существующей базы. После отключения источник должен оставаться отключённым и после рестарта. Уникальность и идемпотентные операции должны выдерживать повторные и параллельные запросы.
- Применяй существующую валидацию ID и обработчик ошибок. Обеспечь стабильный порядок списков. В каталоге маршрутизируй запросы только по активным адаптерам. Отключение сохраняет тайтлы, записи библиотеки, заметки и прогресс.
- Подключение включает существующий адаптер. Динамическая установка исполняемых расширений, ввод произвольного URL, новые парсеры и функция Migrate в эту задачу не входят.

## Общий REST-контракт

| Запрос | Успешный ответ |
| --- | --- |
| `GET /api/v1/extensions` | `200 { "items": Extension[] }` — все зарегистрированные адаптеры. |
| `GET /api/v1/sources` | `200 { "items": Source[] }` — только подключённые. |
| `PUT /api/v1/sources/{sourceId}` без тела | Подключает известный адаптер. Возвращает `200 Source` при первом и повторном запросе. |
| `DELETE /api/v1/sources/{sourceId}` | Отключает известный адаптер. Возвращает `204` при первом и повторном запросе. |

`Source = { sourceId: string; sourceName: string; websiteUrl: string | null }`.
`Extension = Source & { enabled: boolean }`.

Неизвестный ID даёт `404 SOURCE_NOT_FOUND`. Ошибки используют существующий формат `application/problem+json`. Каталог `GET /api/v1/catalog` сохраняет параметры `q` и `sourceId`, ищет только по подключённым источникам и возвращает `{"items":[]}`, если подключений нет. Запрос каталога с известным отключённым `sourceId` даёт `409 SOURCE_DISABLED`. Маршруты карточек, глав, страниц и операции библиотеки сохраняют текущее поведение. Так читатель может продолжить сохранённое чтение после отключения источника из каталога.

Состояние подключений общее для локального экземпляра API. При обновлении или чистом запуске Pepper&Carrot первоначально подключён. Пользователь может отключить и снова подключить его.

## Приёмка

Добавь тесты нового поведения и выполни `.\mvnw.cmd -B -ntp verify`. На живом API проверь оба списка, повторные `PUT` и `DELETE`, неизвестный ID, пустой каталог, `409 SOURCE_DISABLED`, поиск с подключённым источником и чтение из библиотеки после отключения. Проверь состояние после рестарта приложения. Верни исходное состояние подключения. Если для реализации потребуется изменить контракт, зафиксируй причину и синхронизируй контракт с фронтендом до проверки интеграции.

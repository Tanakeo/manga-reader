# План каталога MangaDex и офлайн-чтения Pepper&Carrot

Оба этапа реализованы. Актуальные маршруты, настройки и результаты проверок приведены в [отчёте](catalog-and-offline-report.md). Остальной текст сохраняет исходный план от 16 ноября 2026 года.

## Текущее состояние

- `CatalogController` принимает `sourceId` и `q`, выбирает подключённые адаптеры через `SourceConnectionService`, затем передаёт результаты в `TitleRepository.sync`. Карточка синхронизируется тем же методом. У каждого тайтла постоянный локальный `titles.id`, а внешний ключ поиска — пара `(source_id, external_title_id)`. `LibraryService.create` также использует `sync`, после чего библиотека ссылается на локальный ID. [Контроллер каталога](../src/main/java/io/github/mangareader/catalog/CatalogController.java) · [Репозиторий тайтлов](../src/main/java/io/github/mangareader/library/TitleRepository.java) · [Библиотека](../src/main/java/io/github/mangareader/library/LibraryService.java)
- `MangaDexSource` запрашивает до 24 результатов, задаёт условия языка и рейтинга, использует отдельные кэши поиска и карточки. `readTitle` уже читает год из `attributes.year` и формирует локализованные поля. Теги пока не входят в `SourceTitle`. Последняя миграция `V4__localize_catalog_titles.sql` добавляет названия, статус публикации и год. [Адаптер MangaDex](../src/main/java/io/github/mangareader/source/mangadex/MangaDexSource.java) · [Миграции](../src/main/resources/db/migration/)
- `PepperCarrotSource.getPages` уже собирает упорядоченный список изображений конкретного перевода и атрибуцию. Это онлайн-манифест с URL источника. Angular Reader по обычному маршруту отдельно запрашивает тайтл, главы и страницы, а проверка нового прогресса в библиотеке обращается в адаптер. Для полного офлайн-сценария нужен отдельный путь загрузки этих данных. Spring Boot работает на хосте, Compose содержит PostgreSQL с именованным томом. [Pepper&Carrot](../src/main/java/io/github/mangareader/source/peppercarrot/PepperCarrotSource.java) · [Angular Reader](../../frontend/src/app/reader.ts) · [Compose](../compose.yaml)

## Этап 1. Теги и фильтры каталога

### Какие данные даёт MangaDex

Карточка `GET /manga/{id}` возвращает `data.attributes.tags`, поиск `GET /manga` — `data[].attributes.tags`. В обоих случаях это массив объектов с `id`, `attributes.group` и `attributes.name`. Справочник доступен по `GET /manga/tag`. В проверке справочник вернул 77 тегов из групп `genre`, `theme`, `format` и `content`, а названия в ответе не содержали ключа `ru`. Карточка `dc07afaa-643a-4bf4-a9d0-b21ecc101736` содержала, среди прочих, `Reincarnation` и `Long Strip`. Их UUID использованы в примере контракта ниже. [Справочник и схема Tag в OpenAPI](https://gitlab.com/mangadex-pub/mangadex-api-docs/-/raw/main/static/api.yaml#L3175) · [Карточка, проверенная в живом API](https://api.mangadex.org/manga/dc07afaa-643a-4bf4-a9d0-b21ecc101736)

`GET /manga` принял повторяемый `includedTags[]`, `includedTagsMode=AND` и отдельно каждую из сортировок `order[relevance]`, `order[year]` и `order[latestUploadedChapter]`. В каждом пробном запросе все возвращённые тайтлы содержали оба выбранных тега. Сортировку выполняет источник. В проверенной карточке `latestUploadedChapter` содержал UUID главы. `updatedAt` отражает изменение тайтла и для этой сортировки не подходит. Точная дата последней главы в ответе «Кадра» на этом этапе не требуется. [Параметры поиска MangaDex](https://gitlab.com/mangadex-pub/mangadex-api-docs/-/raw/main/static/api.yaml#L136)

### Модель тегов и миграция V5

DTO `SourceTag { id: string; group: string; names: Record<string, string> }`. `id` для MangaDex — UUID источника в каноническом виде. Группу сохраняем строкой из источника. `names` содержит предоставленные источником локализации. Angular выбирает язык интерфейса, затем `en`, затем первое непустое название по отсортированному коду языка. Подписи групп можно локализовать в Angular; ключи `group` и названия из API при этом сохраняются.

Предлагаемая миграция `V5__add_title_tags.sql`:

| Объект | Предлагаемая схема |
| --- | --- |
| `source_tags` | `source_id varchar(64)`, `external_tag_id varchar(200)`, `tag_group text NOT NULL`, `names jsonb NOT NULL`, `source_version integer NULL`, `updated_at timestamptz NOT NULL`. PK `(source_id, external_tag_id)`. Проверка, что `names` — JSON-объект. |
| `title_tags` | `title_id uuid`, `source_id varchar(64)`, `external_tag_id varchar(200)`. PK `(title_id, source_id, external_tag_id)`. FK `(title_id, source_id) → titles(id, source_id) ON DELETE CASCADE` и FK `(source_id, external_tag_id) → source_tags`. Обратный индекс `(source_id, external_tag_id, title_id)`. |
| `titles` | Добавить `tags_synced_at timestamptz NULL` и `tags_source_version integer NULL`. Добавить `UNIQUE (id, source_id)` для составного FK, чтобы БД отклоняла связь тайтла с тегом другого источника. |

### Синхронизация старых и новых тайтлов

1. Общий разбор MangaDex преобразует теги из поиска и карточки. Во внутренней модели различаются полный список, в том числе подтверждённый пустой, и отсутствие достоверных данных о тегах. Ошибка парсинга или пропуск поля оставляет прежние связи. Подтверждённый пустой список удаляет связи этого тайтла. Для DTO карточки `tags` всегда массив.
2. `TitleRepository.sync` сохраняет прежний локальный `titles.id`. В одной короткой транзакции репозиторий блокирует нужную строку тайтла, обновляет справочник по внешним ID и приводит набор связей к полному снимку. Снятые связи удаляются, записи справочника сохраняются для других тайтлов. При параллельных запросах версия тайтла MangaDex и время фактического получения снимка защищают связи от записи более старого ответа из кэша. Для имён и групп используется версия самого тега при её наличии. Запросы к MangaDex выполняются вне транзакции. Справочник сначала загружается из источника, затем записывается в БД.
3. После V5 у прежних тайтлов `tags_synced_at IS NULL`. Первый успешный каталог, карточка или добавление в библиотеку заполняет связи через существующий `sync`. Для тайтлов, которые больше не открывают, предусмотреть явный возобновляемый backfill небольшими пачками по `external_title_id`. Например, до 50 ID за запрос `GET /manga?ids[]=…&limit=50` с текущим ограничением рейтингов. В живом API проверен этот способ получения ресурса по `ids[]`. Backfill обновляет только вернувшиеся тайтлы. Отсутствующий результат или сбой оставляют существующие данные и попадают в отчёт запуска. При `429` сохраняется позиция и учитывается пауза из клиента MangaDex. [Поиск MangaDex по ids[]](https://gitlab.com/mangadex-pub/mangadex-api-docs/-/raw/main/static/api.yaml#L210)
4. При чтении карточки загрузить теги набором по локальному ID через `title_tags` и `source_tags`. Результат поиска сохраняет порядок источника. `TitleSummary` и записи библиотеки сохраняют текущий размер DTO. Flyway выполняет только SQL. Запуск приложения и миграция возможны при недоступности MangaDex.

### REST-контракт каталога для Angular

| Метод и маршрут | Ответ |
| --- | --- |
| `GET /api/v1/sources/{sourceId}/tags` | `200 {"items": SourceTag[]}`. Для подключённого MangaDex выдаётся справочник в стабильном порядке `group`, отображаемое имя, `id`. Название для серверного порядка берётся из `en` с запасным вариантом по коду языка. |
| `GET /api/v1/sources/{sourceId}/titles/{externalTitleId}` | Текущий `TitleDetail` плюс `tags: SourceTag[]`. Для адаптеров без тегов приходит `[]`. У известных отключённых источников прямые ссылки на карточку сохраняют текущее поведение. |
| `GET /api/v1/catalog` | Текущий `{"items": TitleSummary[]}`. Сохраняются `sourceId` и `q`. Новые параметры описаны ниже. |

- `tagId` — повторяемый query-параметр с UUID. Выдача содержит тайтлы со всеми выбранными тегами. Дубликаты сводятся к одному ID. Предлагаемый лимит — 10 значений в запросе. Angular передаёт значения отдельными параметрами через `HttpParams.append`.
- `sort` — `relevance`, `year_asc`, `year_desc` или `latest_chapter_desc`. Год означает год исходной публикации, порядок пустых годов определяет MangaDex. Последняя глава означает последнюю загрузку по индексу MangaDex, а не последнюю главу конкретного языка. Без `sort` сохраняется текущий порядок. При `relevance` с непустым `q` используем `order[relevance]=desc`, без `q` — текущий `order[followedCount]=desc`. Год передаётся как `order[year]=asc/desc`, последняя глава — `order[latestUploadedChapter]=desc`.
- При передаче любого `tagId` или явного `sort` обязателен `sourceId`. Запрос без этих параметров остаётся совместимым с текущей агрегированной выдачей всех подключённых адаптеров. Angular не передаёт `sort` для состояния по умолчанию в общем каталоге.
- Ввести внутри бэкенда объект `CatalogQuery` и поддержку расширенного каталога для MangaDex. Обычный поиск других адаптеров продолжает использовать существующий `searchTitles(String)`. В запрос MangaDex передаются `title`, `includedTags[]`, `includedTagsMode=AND` и `order[…]` одновременно с действующим `limit=24`. Порядок фильтрации определяет MangaDex. Фильтрации уже обрезанных 24 записей и локальной пересортировки нет. Действующие параметры рейтингов, языков и доступности глав сохраняются. Ключ кэша учитывает текст, канонический набор ID и сортировку.
- Справочник MangaDex можно кэшировать в памяти с TTL до 6 часов и одним запросом обновления на весь экземпляр. UUID проверяется по полному справочнику источника. При промахе допустимо обновить его досрочно с ограничением частоты. Если актуального справочника нет и обновление не удалось, использовать ошибки источника. Пустой результат поиска `200 {"items":[]}` означает корректный запрос без совпадений.

Пример запроса:

```http
GET /api/v1/catalog?sourceId=mangadex&q=prison&tagId=0bc90acb-ccc1-44ca-a34a-b9f3a73259d0&tagId=3e2b8dae-350e-4ab8-a8ce-016e844b9f0d&sort=year_desc
```

Пример одного элемента справочника или массива `TitleDetail.tags`:

```json
{"id":"0bc90acb-ccc1-44ca-a34a-b9f3a73259d0","group":"theme","names":{"en":"Reincarnation"}}
```

| Условие | Ответ `application/problem+json` |
| --- | --- |
| Нет `sourceId` при запросе с тегами или сортировкой | `400 SOURCE_REQUIRED_FOR_CATALOG_OPTIONS`, ошибка поля `sourceId`. |
| Неверный UUID, неподдерживаемое значение `sort`, превышен лимит тегов | `400 VALIDATION_ERROR`, поле `tagId` или `sort`. |
| Неизвестный источник | `404 SOURCE_NOT_FOUND`. |
| Известный источник отключён | `409 SOURCE_DISABLED` для каталога с явным фильтром и для справочника. Проверка выполняется до обращения к источнику. |
| Подключённый адаптер без поддержки запрошенного фильтра, сортировки или справочника | `422 CATALOG_OPTIONS_UNSUPPORTED`. Обычный поиск по нему работает через `q`. |
| UUID корректен, но отсутствует в успешно полученном справочнике | `422 UNKNOWN_TAG`, `errors[].field = "tagId"`. |
| Сбой MangaDex или PostgreSQL | Существующие `502/503` и коды `SOURCE_BAD_RESPONSE`, `SOURCE_UNAVAILABLE` или `DATABASE_UNAVAILABLE`. |

Контракт согласован с frontend-планом тегов и загрузок. Клиент берёт возможности каталога из существующих полей `supportsTags` и `sorts` в `GET /api/v1/sources`. Применяются значения сортировки из этого документа, список `/library/downloads` и отдельная читалка `/downloads/:id/read`. Для неизвестных тегов ошибка возвращает также `invalidTagIds`. [Frontend-план](../../frontend/docs/catalog-and-offline-plan.md)

Первый frontend-шаг показывает теговые фильтры и сортировку при выбранном MangaDex. Параметры `q`, `sourceId`, повторяемые `tagId` и `sort` читаются из URL, чтобы состояния работали после перезагрузки и при прямой ссылке. Сейчас `q` находится в локальном сигнале компонента. При смене источника очищаются несовместимые теги и сортировка. При ошибке справочника остаётся обычный поиск. Для `UNKNOWN_TAG` интерфейс позволяет сбросить выбор. ## Этап 2. Офлайн-MVP Pepper&Carrot

### Что значит офлайн

Читатель один раз скачивает конкретную главу на конкретном языке. После перезапуска браузер обращается к локальному Angular и Spring Boot. Spring Boot отдаёт локальную карточку из `titles`, снимок главы и атрибуцию из PostgreSQL и изображения из локального каталога. Внешний сайт может быть недоступен. Локальные Angular, Spring Boot, PostgreSQL и папка с файлами нужны при чтении. Режим работы браузера без локального сервера относится к отдельной задаче.

`PepperCarrotSource.getPages` определяет допустимый язык, порядок страниц и титры. Worker скачивает исходные `low-res` JPG/GIF по уже проверенным адресам из manifest для выбранного перевода. Сохраняем массив страниц с индексами от нуля, название главы, автора, титры участников и перевода, ссылку на оригинал и `CC BY 4.0` со ссылкой. Читалка показывает атрибуцию обычным текстом, доступным офлайн. Изображения сохраняются без изменений. [API Pepper&Carrot](https://www.peppercarrot.com/en/documentation/130_API.html) · [Рекомендации по атрибуции](https://www.peppercarrot.com/en/documentation/120_License_best_practices.html) · [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)

### Хранение и миграция V6

Предлагаемая миграция `V6__add_offline_downloads.sql`:

| Таблица | Поля и ограничения |
| --- | --- |
| `chapter_downloads` | `id uuid PK`, `title_id uuid REFERENCES titles(id) ON DELETE RESTRICT`, `chapter_id varchar(200)`, `language varchar(32)`, `status`, `attempt_no integer`, `chapter_title text`, `attribution jsonb`, `page_count integer NULL`, `downloaded_pages integer NOT NULL DEFAULT 0`, `error_code`, `error_detail`, `created_at`, `updated_at`. Уникальный ключ `(title_id, chapter_id, language)`. Индекс очереди `(status, created_at, id)`. Задача хранится независимо от записи библиотеки. |
| `download_pages` | `download_id uuid REFERENCES chapter_downloads(id) ON DELETE CASCADE`, `page_index integer CHECK (page_index >= 0)`, `storage_key text`, `mime_type`, `size_bytes bigint`, `sha256`. PK `(download_id, page_index)`. В БД храним относительный ключ и метаданные, байты лежат в файловом хранилище. |

По умолчанию `KADR_OFFLINE_DIR=./data/offline` при запуске из `backend/`, каталог вне `target/` и исключён из Git. Spring Boot на хосте пользуется этой папкой. Если сервер позже будет запущен в Docker, выделить для изображений отдельный именованный том, например `offline-pages:/data/offline`, и задать абсолютный путь в контейнере. Текущий том PostgreSQL остаётся отдельным. Для восстановления нужны согласованные копии БД и каталога с изображениями.

### Жизненный цикл

- Создание делает атомарную вставку по уникальному ключу. Повторный запрос для той же главы и языка возвращает ту же задачу. Один worker забирает `QUEUED`, атомарно переводит её в `DOWNLOADING` и записывает номер попытки. Сетевые операции выполняются вне транзакции. Разные переводы одной главы получают разные записи.
- Worker получает манифест через адаптер, проверяет язык и страницы. URL берутся из манифеста только с ожидаемого HTTPS-хоста и пути Pepper&Carrot. Применяются таймаут, допустимые фактические форматы JPG/GIF, предел размера файла и главы. Ключи файлов генерируются на сервере из ID загрузки и индекса. Операции с файлами ограничены настроенным корнем.
- Частичные файлы складываются во временный каталог попытки на той же файловой системе. После проверки всех страниц worker атомарно перемещает каталог в итоговое место, затем в одной транзакции записывает `download_pages`, снимок атрибуции и статус `READY`. HTTP-чтение доступно только для `READY`. Если приложение завершилось после перемещения и до подтверждения БД, восстановление убирает непубликованный каталог при обработке прерванной попытки. Смена статуса учитывает номер попытки, чтобы старая попытка не могла завершить повторную.
- Сетевой отказ, неподдерживаемый перевод, исчерпанный лимит или проблема записи переводят задачу в `FAILED` с понятным `error.code` и `error.detail`. Повтор переводит `FAILED → QUEUED` для того же ID. Worker очищает файлы и строки страниц предыдущей неудачной попытки и скачивает главу заново по текущему манифесту. При старте одного экземпляра `QUEUED` подхватываются, прерванные `DOWNLOADING` становятся `FAILED` с кодом `DOWNLOAD_INTERRUPTED`. Невалидная или исчезнувшая локальная страница даёт `OFFLINE_FILE_MISSING` и переводит соответствующую попытку из `READY` в `FAILED`, чтобы загрузку можно было повторить.
- Удаление `READY` или `FAILED` сначала переводит задачу в `DELETING` и прекращает выдачу страниц, затем очищает файлы и удаляет запись с дочерними страницами. Операция возобновляется после перезапуска. При временном сбое очистки задача остаётся видимой с сообщением об ошибке и её очистку можно повторить. Удаление активной загрузки даёт `409 DOWNLOAD_IN_PROGRESS`. Удаление скачанных страниц сохраняет тайтл, библиотеку, заметку и прогресс.
- Для офлайн-читалки Angular использует маршрут `/downloads/:id/read`, локальные сведения о тайтле из загрузки и манифест из БД. Обычные запросы тайтла, глав, онлайн-страниц и внешней обложки этот экран не делает. В MVP навигация ведёт назад в «Загрузки», соседние главы в офлайн-манифесте равны `null`. Для сохранения позиции существующий `PATCH /api/v1/library/{entryId}` сначала сверяет `pageIndex` с `READY`-манифестом той же главы и языка. При отсутствии такой загрузки остаётся текущая онлайн-проверка.

### REST-контракт загрузок для Angular

`Download` содержит `id`, `title: TitleSummary`, `chapterId`, `language`, `chapterTitle: string | null`, `status`, `pageCount: number | null`, `downloadedPages: number`, `error: {code: string, detail: string} | null` и `updatedAt`. По `status` Angular показывает очередь, прогресс, кнопку открытия, повтор или удаление. Повторное получение состояния идёт периодическим `GET` с паузой, например 2 секунды, только пока задача активна.

| Метод и маршрут | Успешный ответ и поведение |
| --- | --- |
| `POST /api/v1/downloads` | JSON `{"sourceId":"peppercarrot","externalTitleId":"pepper-and-carrot","chapterId":"ep01_Potion-of-Flight","language":"ru"}`. `202 Download` для новой, очередной или выполняющейся задачи. `200 Download` для существующей `READY` или `FAILED`. `Location: /api/v1/downloads/{id}`. Синтаксис и тип источника проверяются при приёме, доступность главы и перевода — в worker. |
| `GET /api/v1/downloads` | `200 {"items": Download[]}`. Сортировка `updatedAt DESC, id`. Пустой список поддерживается. |
| `GET /api/v1/downloads/{id}` | `200 Download`. Для неизвестного UUID — `404 DOWNLOAD_NOT_FOUND`. |
| `POST /api/v1/downloads/{id}/retry` | `202 Download` при переходе из `FAILED` или при повторе уже запущенной попытки. Для `READY` — `200` с текущей задачей. `DELETING` даёт `409 DOWNLOAD_DELETING`. |
| `DELETE /api/v1/downloads/{id}` | `202 Download` на время очистки или её повтора. После очистки тот же запрос возвращает `204` без тела. Новое скачивание по этому ключу создаёт новый ID. |
| `GET /api/v1/downloads/{id}/pages` | `200 ChapterPages` в уже знакомой Angular форме с сохранённой атрибуцией, локальными `imageUrl` и последовательными индексами. |
| `GET /api/v1/downloads/{id}/pages/{index}/image` | `200` с бинарным JPG/GIF, верным `Content-Type` и `Cache-Control: no-store`. Для индекса вне манифеста — `404 PAGE_NOT_FOUND`. |

Неверный параметр или тело возвращают `400 VALIDATION_ERROR`. Неизвестный источник возвращает `404 SOURCE_NOT_FOUND`, зарегистрированный источник вне офлайн-MVP — `422 DOWNLOAD_UNSUPPORTED_SOURCE`. Запрос на создание для задачи в `DELETING` даёт `409 DOWNLOAD_DELETING`. Чтение задачи в состоянии, отличном от `READY`, даёт `409 DOWNLOAD_NOT_READY`. Если манифест готов, но файл пропал, возвращается `503 OFFLINE_FILE_MISSING`, интерфейс предлагает повтор. Асинхронные ошибки worker отражаются в `Download.error`. Свойство источника «подключён» управляет каталогом. Уже сохранённое чтение доступно независимо от него.

### Локальная папка или MinIO

| Вариант | Для каких условий |
| --- | --- |
| Локальная папка или отдельный Docker-том | Один экземпляр Spring Boot, учебный проект и демонстрация на одном компьютере. Простые бэкап и перенос вместе с БД, быстрые локальные операции. Требуется место на диске и проверка восстановления. Это выбор для MVP. |
| MinIO или другое S3-совместимое хранилище | Несколько экземпляров backend на разных хостах, общее удалённое хранилище, независимые политики хранения, доступ и резервирование объектов. Появляются развёртывание сервиса, ключи доступа, мониторинг и сетевой путь. Отказоустойчивость зависит от топологии. При переходе сохраняется `storage_key` и контракт Angular, реализация хранилища и публикация файлов меняются. |

Решение пересматриваем при нескольких хостах, требованиях к версионированию, репликации или росте объёма за пределы планируемого локального диска и бэкапа. Само добавление Docker к запуску не требует объектного хранилища. [Доступность MinIO](https://min.io/docs/minio/linux/operations/concepts/availability-and-resiliency.html) · [Версионирование объектов](https://docs.min.io/aistor/administration/objects-and-versioning/versioning/)

### Почему скачивание MangaDex оценивается отдельно

Публичный API MangaDex описывает получение страниц для чтения и требует атрибуцию MangaDex и групп перевода, соблюдение запросов на удаление и отсутствие рекламы или платного доступа. Ссылки MangaDex@Home краткоживущие, а сеть требует отчёт об успехе или сбое каждого запроса к стороннему узлу. Эти условия подходят для уже реализованного онлайн-чтения. Сами по себе они не подтверждают право сохранять и повторно раздавать конкретные главы офлайн. Для отдельного этапа нужны подтверждение условий хранения и право на материал, учёт отзывов доступа и возможность удалить локальные копии по запросу. Для MangaDex в MVP возвращается `DOWNLOAD_UNSUPPORTED_SOURCE`. [Политика MangaDex](https://gitlab.com/mangadex-pub/mangadex-api-docs/-/raw/main/index.md) · [Правила MangaDex@Home](https://gitlab.com/mangadex-pub/mangadex-api-docs/-/raw/main/04-chapter/retrieving-chapter.md)
